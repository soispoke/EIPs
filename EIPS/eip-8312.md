## Abstract

Adds a `UTXO` frame mode to [EIP-8141](./eip-8141.md) frame transactions. A UTXO is a one-shot payment object: created by a deposit to a vault system contract, spent whole by a signed, value-conserving frame. A UTXO's contents are kept in history and proven against per-block openings roots; the only permanent state per UTXO is one spent bit.

## Motivation

Receiving a payment on Ethereum writes permanent state: an account leaf or a storage slot. A one-shot payment does not need persistent state. It needs a value, a recipient, and protection against double spending.

The UTXO frame provides this with minimal state. Existence is proven from append-only history, and consumption is one bit in a packed bitfield, so a spent UTXO leaves a quarter byte of permanent state instead of the 120 bytes of a fresh account leaf. Under [EIP-2780](./eip-2780.md) and [EIP-8037](./eip-8037.md) pricing, a transfer that creates an account costs 21,000 regular gas plus 183,600 state gas; a complete UTXO cycle (create, then spend) costs about 98,500 gas, of which 383 is state gas.

Because gas payment is part of the frame's conservation rule, a recipient can spend a UTXO while holding no ETH. Because the frame declares the full transition as inspectable data, a sponsor can verify its repayment before approving payment.

`UTXO_CREATED_TOPIC` is `keccak256("UtxoCreated(address,address,uint64,uint256)")`. Gas constants are defined under [Gas](#gas).

### The UTXO object

Each UTXO is an opening plus one protocol-assigned index:

```
opening = (source, value, recipient)
index   : uint64
```

- `source` -- the account that created the UTXO.
- `value` -- the amount in wei.
- `recipient` -- the address authorized to spend.
- `index` -- a global monotonic counter assigned at creation.

A UTXO is spent whole. The opening is not stored in state; it is emitted in a log and committed to the creation block's openings root. The only per-UTXO state is a spent bit in the vault's storage, at bit `index & 0xFF` of slot `SLOT_SPENT_BASE + (index >> 8)`.

### Creation

Any account, including a contract, creates a UTXO by calling `UTXO_VAULT` with the 20-byte recipient as calldata and the value attached. The call reverts unless the calldata is exactly 20 bytes, the value is non-zero, and the recipient is non-zero; in particular, a plain transfer with empty calldata reverts, so no value enters the vault without creating a UTXO. On success the vault assigns the next index, increments the counter at `SLOT_NEXT_INDEX`, and emits:

```
UtxoCreated(address indexed source, address indexed recipient, uint64 index, uint256 value)

topics = [UTXO_CREATED_TOPIC, caller, recipient]
data   = index (32 bytes) ++ value (32 bytes)
```

The vault holds all unspent UTXO value. Its code handles deposits only; every other write to its storage or balance is performed by the protocol directly.

At activation, the chain's state MUST include `UTXO_VAULT` with nonce `1` and this runtime code:

```
0x5f3560601c80156014361415173415176048575f54806001015f555f5234602052337f3b19241465a47bc187f1d9c7db70834855a907183742a4b63aa824c576296f5e60405fa3005b5f5ffd
```

The runtime code is produced by the geas program below, also provided in [`utxo_vault.eas`](../assets/eip-8312/utxo_vault.eas) together with a Solidity reference implementation, [`UtxoVault.sol`](../assets/eip-8312/UtxoVault.sol).

```asm
#define utxoCreatedTopic = keccak256("UtxoCreated(address,address,uint64,uint256)")

        ;; recipient = calldata[0:20]
        push0               ; [0]
        calldataload        ; [recipient<<96]
        push 96             ; [96, recipient<<96]
        shr                 ; [recipient]

        ;; require calldatasize == 20 and callvalue != 0 and recipient != 0
        dup1                ; [recipient, recipient]
        iszero              ; [recipient==0, recipient]
        push 20             ; [20, recipient==0, recipient]
        calldatasize        ; [cds, 20, recipient==0, recipient]
        eq                  ; [cds==20, recipient==0, recipient]
        iszero              ; [cds!=20, recipient==0, recipient]
        or                  ; [bad, recipient]
        callvalue           ; [value, bad, recipient]
        iszero              ; [value==0, bad, recipient]
        or                  ; [bad, recipient]
        jumpi @fail         ; [recipient]

        ;; index = sload(0); sstore(0, index + 1)
        push0               ; [0, recipient]
        sload               ; [index, recipient]
        dup1                ; [index, index, recipient]
        push 1              ; [1, index, index, recipient]
        add                 ; [index+1, index, recipient]
        push0               ; [0, index+1, index, recipient]
        sstore              ; [index, recipient]

        ;; log data = index ++ value
        push0               ; [0, index, recipient]
        mstore              ; [recipient]
        callvalue           ; [value, recipient]
        push 32             ; [32, value, recipient]
        mstore              ; [recipient]

        ;; emit UtxoCreated(source=caller, recipient, index, value)
        caller              ; [caller, recipient]
        push utxoCreatedTopic ; [topic, caller, recipient]
        push 64             ; [64, topic, caller, recipient]
        push0               ; [0, 64, topic, caller, recipient]
        log3                ; []
        stop

fail:
        push0               ; [0, recipient]
        push0               ; [0, 0, recipient]
        revert
```

### Openings roots

At the end of each block `N`, after all transactions, the client performs a system operation on the vault's storage:

1. Let `leaves` be the leaf of every UTXO created in block `N`, in index order, where `leaf = keccak256(index_be8 ++ source ++ recipient ++ value_be32)`. Write `merkle_root(leaves)` to slot `SLOT_RING_BASE + N % RING_SIZE`.
2. If `N % BATCH_SIZE == BATCH_SIZE - 1`, let `roots` be the openings roots of blocks `N - BATCH_SIZE + 1` through `N`, in block order, and write `merkle_root(roots)` to slot `SLOT_BATCH_BASE + N // BATCH_SIZE`.

```python
def merkle_root(leaves):
    if len(leaves) == 0:
        return b"\x00" * 32
    while len(leaves) & (len(leaves) - 1) != 0:
        leaves.append(b"\x00" * 32)
    while len(leaves) > 1:
        leaves = [keccak256(leaves[i] + leaves[i + 1])
                  for i in range(0, len(leaves), 2)]
    return leaves[0]
```

A UTXO becomes spendable in the block after its creation, since its openings root is only written at the end of the creation block.

### UTXO frame

The frame `mode` table of EIP-8141 is extended:

| `mode` | Name        | Summary                       |
|--------|-------------|-------------------------------|
| 3      | `UTXO` mode | Frame declares a UTXO spend   |

A UTXO frame executes no EVM code. Its `data` is the RLP serialization of a spend:

```
spend = [actors, inputs, utxo_outs, account_outs, change_index, payer,
         max_fee_per_gas, max_priority_fee_per_gas, max_gas_limit]

actors       = [address, ...]
inputs       = [[index, creation_block, source, recipient, value,
                 position, siblings, batch_siblings], ...]
utxo_outs    = [[recipient, value], ...]
account_outs = [[recipient, value], ...]
```

Per input, `index` and `creation_block` are signed; `source`, `recipient`, `value`, `position`, `siblings`, and `batch_siblings` are the witness, read from the proven opening rather than trusted. All other spend fields are signed.

#### Spend hash

```python
def spend_hash(tx, spend):
    signed_inputs = [[i.index, i.creation_block] for i in spend.inputs]
    payload = rlp([tx.chain_id, spend.actors, signed_inputs, spend.utxo_outs,
                   spend.account_outs, spend.change_index, spend.payer,
                   spend.max_fee_per_gas, spend.max_priority_fee_per_gas,
                   spend.max_gas_limit])
    return keccak256(bytes([SPEND_MAGIC]) + payload)
```

For each address in `actors`, `tx.signatures` must contain an entry with a protocol-validated scheme, `resolved_signer` equal to the actor, and `msg` equal to the spend hash. These entries validate under the normal EIP-8141 rules before any frame executes.

#### Constraints

The static constraint `assert frame.mode < 3` of EIP-8141 becomes `assert frame.mode < 4`. For a UTXO frame at position `i`, the following must hold, or the transaction is invalid:

```python
assert frame.flags == 0
assert frame.target is None
assert frame.value == 0
assert i == 0 or tx.frames[i - 1].flags & ATOMIC_BATCH_FLAG == 0

spend = decode(frame.data)  # exact decoding, no trailing bytes

assert len(spend.actors) >= 1 and pairwise_distinct(spend.actors)
assert all(len(a) == 20 for a in spend.actors)
assert len(spend.inputs) >= 1
assert strictly_increasing([i.index for i in spend.inputs])
for inp in spend.inputs:
    assert inp.index < 2**64 and inp.creation_block < 2**64
    assert len(inp.source) == 20 and len(inp.recipient) == 20
    assert inp.value < 2**256
    assert len(inp.siblings) <= 32
    assert inp.position < 2**len(inp.siblings)
    assert len(inp.batch_siblings) in (0, 13)

outs = spend.utxo_outs + spend.account_outs
assert spend.change_index < len(spend.utxo_outs)
for j, out in enumerate(outs):
    assert len(out.recipient) == 20 and out.recipient != address(0)
    assert out.value < 2**256
    assert out.value == 0 if j == spend.change_index else out.value > 0

assert spend.max_fee_per_gas < 2**256 and spend.max_priority_fee_per_gas < 2**256
assert spend.max_gas_limit < 2**64

assert len(spend.payer) in (0, 20)  # empty (written payer == 0) means self-funded
assert spend.payer != UTXO_VAULT
if spend.payer == 0:
    assert tx.sender == UTXO_VAULT
    assert len(tx.frames) == 1
if tx.sender == UTXO_VAULT:
    assert tx.nonce == 0
    assert len(tx.blob_versioned_hashes) == 0
```

`tx.sender` may be `UTXO_VAULT` in the sponsored case as well. A transaction whose sender is `UTXO_VAULT` but which contains no UTXO frame is invalid.

When `tx.sender == UTXO_VAULT`:

- the sender nonce check is skipped and no nonce is incremented, including by `APPROVE(APPROVE_PAYMENT)`,
- the `sender_approved` precondition of `APPROVE(APPROVE_PAYMENT)` is waived.

#### Execution

When the frame loop reaches a UTXO frame, the protocol performs the steps below. If any check fails, the transaction is invalid, as with a reverting `VERIFY` frame.

Before the frame loop, initialize an empty `spent_overlay` scoped to the transaction. It records spent-bit writes from successful UTXO frames. Reads of spent bits include this overlay. The overlay is outside the frame revert journal, but is discarded if the transaction is invalid.

1. Compute `utxo_frame_gas` (see [Gas](#gas)). If `frame.gas_limit < utxo_frame_gas`, the transaction is invalid; otherwise the frame consumes `utxo_frame_gas`. Part of the account-output reserve may be returned at settlement.
2. Check the fee caps:

    ```python
    assert tx.max_fee_per_gas <= spend.max_fee_per_gas
    assert tx.max_priority_fee_per_gas <= spend.max_priority_fee_per_gas
    assert tx_gas_limit <= spend.max_gas_limit
    ```

3. For each input, verify the opening and collect its spent-bit write in `frame_spent`. Checks include writes already present in `spent_overlay` and `frame_spent`.

    ```python
    frame_spent = {}

    def verify_input(inp, block_number):
        leaf = keccak256(inp.index.to_bytes(8, "big") + inp.source +
                         inp.recipient + inp.value.to_bytes(32, "big"))
        root = fold(leaf, inp.position, inp.siblings)
        if len(inp.batch_siblings) == 0:
            assert 0 < block_number - inp.creation_block <= RING_SIZE
            assert root == vault_slot(SLOT_RING_BASE + inp.creation_block % RING_SIZE)
        else:
            batch = inp.creation_block // BATCH_SIZE
            assert block_number >= (batch + 1) * BATCH_SIZE
            root = fold(root, inp.creation_block % BATCH_SIZE, inp.batch_siblings)
            assert root == vault_slot(SLOT_BATCH_BASE + batch)
        assert inp.recipient in spend.actors

        word_slot = SLOT_SPENT_BASE + (inp.index >> 8)
        bit = 1 << (inp.index & 0xFF)
        spent_word = (vault_slot(word_slot)
                      | spent_overlay.get(word_slot, 0)
                      | frame_spent.get(word_slot, 0))
        assert spent_word & bit == 0
        frame_spent[word_slot] = frame_spent.get(word_slot, 0) | bit

    def fold(node, position, siblings):
        for sibling in siblings:
            if position & 1:
                node = keccak256(sibling + node)
            else:
                node = keccak256(node + sibling)
            position >>= 1
        return node
    ```

4. Check conservation and set the payer. `max_cost` is the transaction's maximum cost, the value of `TXPARAM(0x06)`.

    ```python
    spent_value = sum(inp.value for inp in spend.inputs)
    signed_out  = sum(out.value for out in outs)  # change entry is zero

    if spend.payer == 0:
        assert payer is None
        assert spent_value >= signed_out + max_cost
        payer = UTXO_VAULT  # collect max_cost from the vault balance
    else:
        assert spent_value >= signed_out
    ```

5. After all checks above succeed, merge `frame_spent` into `spent_overlay`. The writes are visible to later UTXO frames and are committed with the transaction. A later frame failure does not undo them unless it makes the transaction invalid.

If `spend.payer != 0`, the transaction is invalid unless, after all frames, `payer == spend.payer`. Since a transaction has a single payer, every sponsored UTXO frame in it must name the same one, and a self-funded spend is always the only frame in its transaction.

#### Settlement

At the end of the transaction, after all frames have executed, the protocol settles each UTXO frame, in frame order. Settlement cannot fail, because execution proved every frame solvent.

```python
new_account_recipients = set()
for out in spend.account_outs:              # evaluated before any transfer below
    if (account_exists(out.recipient)
            or out.recipient in new_account_recipients):
        refill_state_gas(GAS_NEW_ACCOUNT_STATE)  # reduces the frame's gas used
    else:
        new_account_recipients.add(out.recipient)

fee = actual_fee if payer == UTXO_VAULT else 0  # gas_used * effective_gas_price, after the returns above
change_value = spent_value - signed_out - fee
source = spend.actors[0] if len(spend.actors) == 1 else UTXO_VAULT

for j, out in enumerate(outs):
    value = change_value if j == spend.change_index else out.value
    if j < len(spend.utxo_outs):
        index = vault_slot(SLOT_NEXT_INDEX)
        set_vault_slot(SLOT_NEXT_INDEX, index + 1)
        emit_log(UTXO_VAULT, [UTXO_CREATED_TOPIC, source, out.recipient],
                 index.to_bytes(32, "big") + value.to_bytes(32, "big"))
    else:
        state.balance[UTXO_VAULT] -= value
        state.balance[out.recipient] += value
```

`account_exists` follows the existence rule of [EIP-8037](./eip-8037.md) and is evaluated before any of the frame's settlement transfers is applied; a frame's checks see the effects of frames settled before it. Only the first output to each recipient that does not yet exist retains the reserve for a new account. The returned reserves are finalized before the transaction's gas used, fee, and refund are computed. Logs emitted by settlement are appended to the UTXO frame's receipt entry, and the created UTXOs join the current block's openings tree. When `payer == UTXO_VAULT`, the standard payer flow applies to the vault: the maximum cost is collected at frame execution and unpaid gas is refunded to the vault, so the vault is debited exactly the actual fee, distributed per [EIP-1559](./eip-1559.md).

#### Gas

| Name                    | Value    | Derivation                                                                                       |
|-------------------------|----------|--------------------------------------------------------------------------------------------------|
| `GAS_UTXO_FRAME`        | `13000`  | `COLD_STORAGE_ACCESS + STORAGE_WRITE` ([EIP-8038](./eip-8038.md)): the `SLOT_NEXT_INDEX` update  |
| `GAS_UTXO_INPUT`        | `16048`  | `2 × COLD_STORAGE_ACCESS + STORAGE_WRITE + 48`: root read, spent-bit write, 80-byte leaf hash    |
| `GAS_UTXO_SIBLING`      | `42`     | `keccak256` of one 64-byte node: `30 + 2 × 6`                                                    |
| `GAS_UTXO_OUT`          | `2012`   | the creation log: `375 + 3 × 375 + 64 × 8`                                                       |
| `GAS_UTXO_ACCOUNT_OUT`  | `9000`   | `COLD_ACCOUNT_ACCESS + TX_VALUE_COST + TRANSFER_LOG_COST` ([EIP-2780](./eip-2780.md))            |
| `GAS_UTXO_SPENT_STATE`  | `383`    | `STATE_BYTES_PER_STORAGE_SET × CPSB / 256` ([EIP-8037](./eip-8037.md)), rounded up               |
| `GAS_NEW_ACCOUNT_STATE` | `183600` | `STATE_BYTES_PER_NEW_ACCOUNT × CPSB` ([EIP-8037](./eip-8037.md))                                 |

```python
utxo_frame_gas = (
    GAS_UTXO_FRAME
    + sum(GAS_UTXO_INPUT
          + GAS_UTXO_SIBLING * (len(inp.siblings) + len(inp.batch_siblings))
          + GAS_UTXO_SPENT_STATE
          for inp in spend.inputs)
    + GAS_UTXO_OUT * len(spend.utxo_outs)
    + (GAS_UTXO_ACCOUNT_OUT + GAS_NEW_ACCOUNT_STATE) * len(spend.account_outs)
)
```

For a frame transaction, the `tx_gas_limit` defined by EIP-8141 is `tx.gas` under EIP-8037. The costs before `sum(frame.gas_limit for all frames)` in the EIP-8141 formula are `intrinsic_gas`; the frame gas limits are execution gas. A UTXO frame's `gas_limit` bounds the sum of regular gas and state gas charged to that frame. Each charge also updates the corresponding EIP-8037 transaction counter. State-gas charges use the transaction's state-gas reservoir. `refill_state_gas` follows the EIP-8037 LIFO refill rule, reduces the UTXO frame's gas used by the refilled amount, and does not make that gas available to a later frame.

Storage components are charged at the cold rate unconditionally. At settlement, each account output whose recipient already exists returns its `GAS_NEW_ACCOUNT_STATE` reserve as unused gas.

Under the two-dimensional metering of [EIP-8037](./eip-8037.md), `GAS_UTXO_SPENT_STATE` and `GAS_NEW_ACCOUNT_STATE` are charged to the state-gas dimension; all other components are regular gas. `frame.data` is charged through `frame_data_cost` of [EIP-8141](./eip-8141.md), and actor signatures through its per-signature costs.

### Mempool

A self-funded spend (`spend.payer == 0`, a single UTXO frame) is recognized as its own validation prefix. Its validity depends only on transaction fields and the vault's protocol state: the openings roots, the batch roots, and the spent bits. Signature validation and `utxo_frame_gas` count toward `MAX_UTXO_VERIFY_GAS = 400000`, a policy bound that replaces `MAX_VERIFY_GAS` for these transactions.

In a sponsored transaction, UTXO frames may appear after the validation prefix even though their failure invalidates the transaction. This is an explicit exception to the rule that no `VERIFY`-like frame follows the prefix. Nodes must run the frames' checks at admission; their combined `utxo_frame_gas`, together with the actor signature validation, counts toward `MAX_UTXO_VERIFY_GAS` rather than `MAX_VERIFY_GAS`. The sponsor's `pay` frame is subject to the paymaster rules of [EIP-8141](./eip-8141.md), whether the transaction's sender is the sponsor or the vault.

Every admitted transaction containing a UTXO frame reserves each input `index`. After validation, a node MUST atomically recheck and reserve the full input set. If no index is reserved, the transaction may be admitted. If every reserved index belongs to one pending transaction with the same sorted input set, the new transaction may replace it subject to the node's fee bump rules. Any other overlap is rejected. Removal releases the full input set atomically. When a block sets spent bits, transactions spending those indices are evicted.

For transactions whose sender is `UTXO_VAULT`, these input reservations replace the EIP-8141 limit of one pending transaction per sender. Other senders remain subject to that limit. A self-funded transaction needs no separate vault balance reservation because its locked inputs are disjoint from those of every other pending transaction and its conservation check reserves its maximum cost. Sponsored transactions remain subject to the EIP-8141 paymaster rules.

## Rationale

### A mode, not a target

A spend is not a contract call: it has no meaningful caller, callee, or value transfer, and no code should run. Modeling it as a `VERIFY` frame with a special target would give it call semantics it does not have and make the protocol recognize an address instead of a declared intent. A mode states directly that the frame is a protocol object with its own validation and settlement.

### Store consumption, prove existence

A "can this still be spent?" check answers two questions: did it exist, and was it used. Bitcoin answers both with presence in the UTXO set, which forces every unspent object into state. Here the questions are split: existence is proven from history against an openings root, and only the "used" fact, one bit, is kept in state. The permanent cost moves from creation to consumption, and a UTXO that is never spent writes no permanent state at all.

### The openings tree

The chain already commits to creation logs through the receipts root, but a receipt proof carries the full receipt of the creating transaction. A batch payout creating 500 UTXOs would force each spender to ship that whole receipt as witness. In the openings tree every UTXO is its own leaf, so a proof is a few hundred bytes of plain hashing regardless of how the UTXO was created. `RING_SIZE == BATCH_SIZE` guarantees that a batch is sealed before any of its ring slots is overwritten, so a ring proof can always be upgraded to a batch proof without a gap.

### Witness refresh

Signatures cover every spend field except the witnesses. Anyone can therefore refresh a witness, for example append the batch path once the creation block leaves the ring, without invalidating a signature, so a signed spend can be kept valid indefinitely. A substituted witness either proves the same opening or fails, since the signed `index` pins it.

The openings roots preserve proof validity, but do not preserve the openings or authentication paths needed to reconstruct a missing proof. A holder must retain the opening and its authentication paths, or obtain them from an external history provider. Possession of the recipient key alone does not guarantee spendability once the required history is unavailable.

### Gas inside the conservation rule

A fresh recipient holds no ETH, so the spend must pay for itself. Reserving the transaction's maximum cost inside the conservation rule guarantees the inputs cover the fee before the payer is set, which is what an opcode, running after gas is prepaid, cannot express. The actual fee is lower, and the difference flows to the change output. Because the maximum cost is transaction-scoped, a self-funded spend is the only frame in its transaction; sponsored spends never reference it, which is what lets several share a transaction.

### The change output

The actual fee is unknown at signing time, so one UTXO output is designated by `change_index`, signed with value zero, excluded from conservation, and receives the remainder at settlement. Restricting change to a UTXO output avoids making account creation, and therefore gas used, depend on the final fee. Exactly as in Bitcoin, change is a new output, not a remaining balance.

### The vault as sender

A spend needs no account behind it: with `UTXO_VAULT` as `tx.sender`, no nonce is checked or consumed, since spending an input already makes replay impossible; this is also why such a transaction must contain a UTXO frame. Self-funded spends always take this form and are restricted to a single frame. Sponsored spends may take it too, and this is what makes a sponsor contract practical: it approves payment per transaction after inspecting its repayment, without signing envelopes or consuming nonces, so one sponsor can serve any number of concurrent spends and a witness refresh never invalidates a signature. A sponsor that is a regular account can instead be the sender itself and sign the envelope.

Vault-sender transactions carry no signature over the outer envelope, which is why they forbid blobs and why fee selection within the signed caps and witness refresh are the only malleable surface. The vault itself can never act: its code never calls `APPROVE`, so `SENDER` frames stay invalid and frame execution cannot move its balance.

### Sponsorship

A sponsor inspects the UTXO frame's data with `FRAMEDATALOAD`, checks for an output paying itself at least its cost, and only then approves payment. The decision is answered by reading declared data, not by simulating code. The signed `payer` field binds the spend to that mode: a submitter cannot strip the sponsor and re-run the spend as self-funded.

### Vault solvency

The vault holds every unspent UTXO's value, and conservation bounds each frame's outflows (outputs, fee, and change) by the value of its proven inputs, so settlement never leaves the vault below the sum of unspent claims; forced transfers into the vault, such as `SELFDESTRUCT` or withdrawals, can only push it above. This is also why the vault can always cover the maximum cost it fronts as payer.

### Bundling and aggregation

Several holders can already share one spend: `actors` is a list, each input's recipient must be an actor, and all actors sign the same spend hash. This is interactive, since everyone signs the complete transition, and merges ten stealth payments into one spend and one fee.

Independently signed spends bundle without interaction: any number of sponsored UTXO frames may share a transaction, all naming the same sponsor, which approves once after inspecting each frame's repayment. The bundler can only select, order, and wrap: every field of value is signed per spend, and each spend's fee caps bound the envelope. Bundling amortizes the transaction intrinsic and envelope across spends, saving roughly a quarter of a standalone spend's cost.

Actor signatures are ordinary signature-list entries over an explicit hash, so the aggregation path of [EIP-8141](./eip-8141.md) stays open: no rule in this EIP reads raw signature bytes (sponsors introspect entry metadata only), and the spend hash commits to no signature bytes. A future scheme tag can therefore back many entries with one aggregate, within a transaction or externalized at the block level, without changing the spend format. Vault-sender transactions are the friendliest case: nothing signs the envelope, so signatures can be aggregated even after the spends are signed and in flight. A post-quantum scheme is one more tag in the signature list; its size is what makes bundling and aggregation matter.

### `SPEND_MAGIC`

The prefix `0x81` lies outside the [EIP-2718](./eip-2718.md) transaction type space (`<= 0x7f`), so a spend hash preimage cannot collide with the signing payload of any transaction type.

### Gas costs

Every constant is a sum of primitives from [EIP-8038](./eip-8038.md), [EIP-2780](./eip-2780.md), and [EIP-8037](./eip-8037.md), so future repricings flow through without re-deriving bespoke numbers. An input pays for one root slot read and one spent-word write, both at the cold rate unconditionally, the [EIP-2780](./eip-2780.md) approach to keeping a charge state-independent, plus the 48-gas keccak of its 80-byte leaf ([EIP-7904](./eip-7904.md) leaves keccak pricing unchanged).

A spent-bits slot holds 256 flags, so consuming a UTXO is charged 1/256 of a new slot's state gas: `97,920 / 256 = 382.5`, rounded up to 383. The flat charge is exact on average and independent of which bits happen to share a slot.

An account output pays the marginal recipient cost of a value transfer under [EIP-2780](./eip-2780.md), plus the full new-account reserve. Whether the recipient exists is third-party state, which frame validation must not read; reserving the worst case and returning it at settlement keeps validation static, and the return cannot fail. A UTXO output costs only its log: the openings root is computed at the block boundary from data already in the block, two hashes per leaf, unmetered like the receipts root.

### Costs compared

| Flow                                                        | Regular gas | State gas | New state |
|-------------------------------------------------------------|-------------|-----------|-----------|
| ETH transfer to a fresh account ([EIP-2780](./eip-2780.md)) | 21,000      | 183,600   | 120 B     |
| Vault deposit (creation)                                    | ≈36,500     | 0         | 0 B       |
| Spend, one input, two UTXO outputs                          | ≈62,000     | 383       | 0.25 B    |

The deposit is the 21,000 transfer intrinsic plus calldata and ≈15,200 of vault execution; the spend is the [EIP-8141](./eip-8141.md) intrinsic, ≈500 bytes of frame data, one secp256k1 signature, and `utxo_frame_gas ≈ 33,900` with a depth-10 proof. A 300M-gas block fits about 1,600 fresh-account transfers, since the state-gas dimension saturates first, and adds ≈190 KiB of permanent state. The same block fits about 3,000 complete UTXO cycles, deposit and spend, and adds under 1 KiB. Payment for payment, the cycle costs half the gas and writes 1/480th of the state.

### Mempool bounds

UTXO frames get their own admission bound and may follow the validation prefix because they are unlike arbitrary `VERIFY` code: their cost is computable from the frame alone before any work is done, their checks read only protocol state, and no third-party storage write can invalidate them. `MAX_UTXO_VERIFY_GAS` admits consolidation spends of roughly twenty inputs.

### ETH only

Openings could carry a token address, with conservation enforced per token and gas paid from the ETH bucket only. This is left to a future extension; nothing in the spend format precludes it.

## Backwards Compatibility

This EIP adds a frame mode to an existing transaction type and a system contract, requiring a hard fork. No existing transaction type or opcode changes behavior. At activation the ring and batch slots are zero; spends can reference creations from the fork block onward.

## Security Considerations

### Double spending

Spent bits from a successful UTXO frame are added to the transaction's `spent_overlay`, outside the frame revert journal, so a spend is final once approved even if a later frame reverts. The overlay is discarded if the transaction is invalid. A duplicate input within one frame is excluded by the strictly increasing index rule, and any duplicate across frames or transactions sees the set bit and fails.

### Envelope malleability

For vault-sender transactions, no signature covers the outer envelope. A submitter can re-wrap the transaction, refresh witnesses, and choose envelope fees, but the signed caps bound the damage: at most `max_gas_limit * max_fee_per_gas` can be diverted from the change output into fees, and a substituted witness either proves the same opening or fails, since the signed `index` pins it. Actors should sign tight caps. A sponsor protects itself: inflating the envelope raises the maximum cost its repayment check compares against, and the check fails.

### Mass invalidation

All UTXO frame validation reads protocol state only, never arbitrary account state, so a spend cannot be invalidated by unrelated storage writes. The remaining invalidation vector, two transactions spending the same input, is limited by the one-pending-transaction-per-index mempool rule, mirroring the per-sender rule for nonces.

### Discovery

Recipients discover UTXOs by scanning logs for the vault address with their address in `topics[2]`. Wallets must also match `topics[0]` against `UTXO_CREATED_TOPIC`; matching the recipient topic alone would let a future log shape under the vault spoof a payment.
